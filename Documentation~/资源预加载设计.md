# 框架层资源预加载(Preload / Prewarm)设计

> 状态:📝 设计中(草稿 v0.1)
> 归属:KFramework(UPM `com.isakwong.kframework`)· Module 层新模块 `Preload`
> 依赖:Unity Addressables(经 `IAssetService`)、UniTask、KSignal/EventBus、ServiceLocator

---

## 1. 概述与动机

### 1.1 要解决的问题

`IAssetService`(现 `AssetManager`)解决了"按 path / AssetReference 异步或同步加载 + 缓存",但**不回答**三个问题:

1. **就绪时机** —— 一组资源要赶在某个必经逻辑之前全部可用(尤其 WebGL 下同步 API 只允许命中缓存,否则抛);
2. **释放时机** —— 这组资源是常驻、随玩法阶段切换释放、还是业务手动释放;
3. **进度与门控** —— Loading 屏如何拿到整组进度,业务如何声明"我等这组就绪"。

预加载**不是**"再封装一个批量 `LoadAllAsync` 工具方法",而是框架提供的一个**声明式资源就绪与生命周期模型**:把"一组资源应于何时就绪、何时释放"描述成数据(Profile),由管理器统一执行、持有句柄、调度释放、广播门控信号。预加载只是这个模型在某个窗口开始处的一次批量执行。

### 1.2 目标 / 非目标

| 目标(框架做) | 非目标(业务/后续做) |
|---|---|
| 声明式就绪清单(Profile SO) | **何时触发** —— 由业务在门控窗口调用(菜单驻留 / 切场景 / 用到前) |
| 幂等执行、去重、并发上限、取消 | 规划 Addressable Group / Label 划分 |
| 句柄集中持有与三态释放调度 | 远程组分包下载与下载进度 UI(等 `IAssetService` 增强) |
| 完成信号与"槽就绪"门控 | 业务级按玩法收敛策略 |
| 平台差异(WebGL 同步限制)在内部消化 | |

一句话:**框架提供"就绪与释放的能力与时序",业务提供"载什么、何时载"的意图。**

## 2. 术语与模块定位

### 2.1 分层

框架分层 `Foundation → Core → Module → FrameworkExt`。本模块落在 **Module 层**,与 `AssetManager / SoundManager / UIManager` 同级(Kit 功能模块聚合)。

### 2.2 关键术语

| 术语 | 含义 |
|---|---|
| **槽(Slot)** | 一组资源的就绪单元,用 `SlotKey` 标识。如 `"Bootstrap"`、`"Zone_01"` |
| **就绪清单(PreloadProfile)** | ScriptableObject,描述某 Slot 载入哪些资源 + 执行/释放策略 |
| **就绪(Ready)** | 该 Slot 内所有条目加载完成且缓存可命中 |
| **句柄所有权** | 预加载发起的加载句柄由本管理器集中持有,**绝不下发裸句柄给业务** |

### 2.3 目录与文件

```
Runtime/Core.Unity/Kit/Preload/
├─ IPreloadService.cs      服务接口(供 ServiceLocator / 业务编程)
├─ PreloadService.cs       实现(KSingleton<PreloadService>,同 AssetManager 模式)
├─ PreloadProfile.cs       ScriptableObject:一个槽的就绪清单
└─ PreloadEvents.cs        进度/完成/失败事件载体
```

> 命名空间:Kit 相邻服务(Asset/Config/Sound)现为全局命名空间,本模块与其保持一致;框架统一收敛到 `KFramework.*` 时随队迁移(见「开放问题」)。

## 3. 核心接口(草案)

### 3.1 IPreloadService

```csharp
public interface IPreloadService
{
    // 执行:让某槽就绪(幂等,见 §4)
    UniTask PrepareAsync(PreloadProfile profile,
                         IProgress<PreloadProgress> progress = null,
                         CancellationToken ct = default);

    // 按 SlotKey 查询/等待就绪(幂等:已就绪立即返回)
    bool   IsReady(string slotKey);
    UniTask WaitReadyAsync(string slotKey, CancellationToken ct = default);

    // 显式释放某槽(遵从 Profile 的释放模式,见 §5)
    void   ReleaseProfile(string slotKey);

    // 当前就绪进度(供 Loading UI 轮询 / 快照)
    PreloadProgress GetProgress(string slotKey);

    // 完成 / 失败广播(KSignal / EventBus 事件,见 §7)
}
```

> 入参用 **Profile 对象**而非仅 `slotKey`:允许同一槽内容按入口配置,也省去管理器再维护一套"key→清单"注册表。
> `WaitReadyAsync` 与"事件"二选一即可满足门控;接口同时暴露便于 UI(订阅进度)与逻辑(await 完成)两条消费路径。

### 3.2 PreloadProfile(ScriptableObject)

```csharp
[CreateAssetMenu(menuName = "KFramework/Preload Profile")]
public class PreloadProfile : ScriptableObject
{
    [Tooltip("槽标识;与其它 Profile 重名即视为同一槽(用于去重/门控)")]
    public string slotKey;

    // 资源条目:三种来源(见设计要点)
    public List<AssetReference> references;   // 逐条强引用(预制体/大资源)
    public List<string>         paths;        // 地址/path 字符串(启动小集 Config 等)
    public List<string>         labels;       // 批量:按 Label 拉整组(Gameplay 等)

    [Header("执行策略")]
    public bool  required;          // true=任一失败则整槽失败;false=单点失败降级继续(默认)
    public int   maxConcurrent;     // 0=按平台默认(桌面≥4 / WebGL=1 串行)
    [Tooltip("加载完成后的归属,见 §5")]
    public ReleaseMode releaseMode = ReleaseMode.Session;
}

public enum ReleaseMode
{
    Persistent, // 常驻:管理器持有,直到显式 ReleaseProfile
    Session,    // 会话:随宿主"阶段切换"自动释放(见 §5.3)
    Manual,     // 手动:仅由调用方显式 ReleaseProfile 释放
}
```

设计要点:

- **三种条目来源**:
  - `AssetReference` —— 逐条强引用,构建安全,适合必须精确收敛的细粒度资源;
  - `path` 字符串 —— 启动小集 Config 等,复用 `IAssetService.LoadAssetAsync<Object>(path)` 路径;
  - `label` —— **整组批量**:预载"一个逻辑组/Group 下的全部资产"。Addressable 中 label 会从 folder entry 继承到其下所有子资产,故对"按文件夹(Group)组织"的资源,给该文件夹打一个 label 即可在运行时整体拉取(Group 本身不是运行时加载键,label 才是)。
  三种统一以 `Object` 泛型加载,类型在业务同步/异步访问时按需强转 —— 与既有预热用法一致。
- **required / releaseMode / maxConcurrent** 是三处最小策略点,不加更多配置项(避免过度设计)。

## 4. 幂等与去重语义

管理器以 `SlotKey → SlotState` 维护状态机:

```
Pending → Loading → Ready → Released(可再回 Pending)
              ↓
           Failed(required 时;可重试)
```

规则:

1. **并发去重**:同 `slotKey` 的 `PrepareAsync` 并发调用**合并为同一次执行**,返回同一 `UniTask`,不重复发起加载。
2. **已就绪**:`Ready` 状态下再次 `PrepareAsync` 立即返回(幂等),供"多个入口都调一次"的写法。
3. **条目级幂等**:逐条加载前先经 `IAssetService` 异步接口 —— 其内部对已缓存项直接返回(命中 `_loadedHandles` / `OperationHandle`),管理器本身不再自建一套缓存。**预加载与按需加载共享同一缓存,不是第二条路径。**
4. **释放后可重入**:`Released` 后可再次 Prepare(如回到主菜单再进下一局)。

## 5. 句柄所有权与释放模型

### 5.1 为什么集中持有

`AssetManager.ReleaseAsset(path)` / `ReleaseAssetReference(ref)` 会释放缓存句柄。若预加载发起的句柄散落业务,必然出现"业务以为还活着、框架已放"或相反。因此:

- 管理器记录自己发起过的每一条 `path / AssetReference`;
- 释放只由管理器在**三态之一**触发;
- **不向业务暴露句柄** —— 业务只拿资源对象,经 `IAssetService` 缓存取(同步访问在槽就绪后必命中)。

### 5.2 三态语义

| 模式 | 释放触发 | 适用 |
|---|---|---|
| Persistent | 显式 `ReleaseProfile(slotKey)`(如应用退出 / 明确不再用) | 启动常驻 Config、全流程核心池 |
| Session | 宿主声明"进入下一阶段"时由管理器**自动释放本阶段上一槽** | 关卡/玩法子集:进新局自动腾退旧局资源 |
| Manual | 业务自行决定时机,调 `ReleaseProfile` | 生命周期不规整的临时集合 |

### 5.3 会话释放的触发源(待定,见开放问题)

Manager 不猜测"阶段"边界。提供**显式切换 API**(如 `BeginSession(sessionId)`),由宿主(GameMode / 业务入口)在场景切换、玩法退出时调用;管理器据 profile 的 `Session` 标记自动释放上一 session 载入、且本 session 未再引用的槽。

> 最小版可不引入 Session 语义,先用 Persistent + Manual 两态;Session 作为扩展点。见「落地顺序」。

## 6. 执行、并发、进度、失败、取消

### 6.1 执行与并发

- 逐条目调用 `IAssetService.LoadAssetAsync<Object>(…)`,避免在框架层直接 `Addressables.*`。
- 并发:按 `maxConcurrent` 控制同时 in-flight 数;0 时按平台默认(**Editor/桌面允许并发;WebGL 建议串行或低并发**,因单线程加载抖动与内存峰值更大)。默认值收敛在 PreloadService 一处,业务不感知。
- **不要求总条目预知总量即可开始**,进度基于"已完成/总数"。

### 6.2 进度

`PreloadProgress { string slotKey; int done; int total; bool done; IReadOnlyList<string> failedKeys; }`

- UI 取 `GetProgress(slot)` 轮询或订阅进度事件;远程下载的"字节级百分比"依赖 `IAssetService` 增加下载量查询(见开放问题),本版以计数为准。

### 6.3 失败与取消

- `required=false`(默认):单条失败记日志、计入 `failedKeys`、继续其余,完成后仍广播"完成(含失败)";
- `required=true`:任一条失败 → 整槽 `Failed`,`PrepareAsync` 抛出/返回失败结果,由上层走降级路径;
- 取消:传入 `CancellationToken` 即中止后续条目;已加载完成的条目**保留**(可命中缓存,不浪费),不自动回滚释放。

## 7. 门控信号与上层消费约定

### 7.1 完成信号

- 槽完成(含 `failedKeys`)经 **EventBus 全局广播**(或 KSignal)发送 `PreloadCompletedEvent(slotKey, failedKeys, elapsedMs)`;
- 逻辑侧门控推荐用 `await WaitReadyAsync(slotKey)`(幂等),UI 侧订阅进度事件驱动 Loading 百分比/文案。

### 7.2 对业务的关键约定(平台差异收口处)

> **业务在 `await IPreloadService.WaitReadyAsync(slotKey)` 之后,才可以对该槽资源做同步 `LoadAsset<T>`。**

这条约定把 WebGL"同步 API 只读缓存、否则抛"的平台差异**隔离在预加载语义内部**:框架承诺"槽就绪 ⇒ 该槽资源缓存必命中";业务代码不出现任何平台分支。

## 8. 与现有系统的接缝

| 系统 | 关系 |
|---|---|
| `IAssetService`(AssetManager) | **唯一 I/O 后端**。PreloadService 只调 `LoadAssetAsync` / `ReleaseAsset(Reference)`,不直接触碰 `Addressables`;缓存、Editor 直读、WebGL 命中逻辑全部复用现成实现 |
| ServiceLocator | `PreloadService.OnServiceInit` 中 `ServiceLocator.Register<IPreloadService>(this)`(对齐 `AssetManager`) |
| KGameCore / TModule | 本模块是普通服务,不强制挂 GameMode;若宿主游戏统一走 `KGameCore.RequireSystem` 亦可 |
| EventBus / KSignal | 完成事件广播走现有事件机制 |
| UIManager(Loading 面板) | 只作为**消费方**订阅进度,不反向依赖本模块 |

> 依赖方向仅 `Preload → IAssetService`,无环。

## 9. 验收清单

以下为可测试(建议在 `Tests/` 用 **mock `IAssetService`**,不落真资源):

- [ ] 幂等:同槽并发两次 `PrepareAsync` 只触发一次加载(mock 计数=1);
- [ ] 就绪:槽就绪后,`IAssetService` 的缓存对每条资源可命中(WebGL 路径不再抛);
- [ ] 失败降级:`required=false` 单条失败 → 其余完成、`failedKeys` 上报;`required=true` → 整槽失败;
- [ ] 并发上限生效(`maxConcurrent` 不被突破);
- [ ] 取消:`ct` 取消后不再发起新条目、已载条目保留;
- [ ] 释放:三态各自在正确时机调用底层 `ReleaseAsset(Reference)`,无泄漏/无重复释放;
- [ ] 重入:`Released` 后可再次 Prepare。

## 10. 落地顺序(建议)

1. **核心最小路径(本版范围,直接服务 JASA 初版两槽)**
   `PreloadProfile`(三种条目 path/AssetReference/label)→ `PreloadService` 幂等执行 + 槽状态 + `WaitReadyAsync`/`GetProgress` + mock 单测。释放先做 **Persistent + Manual** 两态,Session 后置(见 §12 初版策略)。
2. **Session 自动释放**:加 `BeginSession(sessionId)` 与 Session 态,由宿主接入场景/玩法切换。
3. **增强(按需)**:`IAssetService` 增加下载量查询,预加载进度升级为字节百分比;远程组分包策略。

> 第 2、3 步在接口上已预留,不在第一步引入,避免过度设计。

## 12. 现状接入与初期策略(JASA)

> 本节记录宿主 JASA 的接入现状与"先简化、后演进"的初版策略,供落地与回看。

### 12.1 现状(资源组织)

- Addressable 按 **folder entry(整目录)** 组织,六个逻辑组:
  `Bootstrap`(Config)/`Gameplay`(武器、消耗品、特效、环境、敌人生成器、门、瓦片地图、交互物、地牢、角色、装备 共 11 目录)/`Shared`/`UI`/`Scenes`/`Default Local Group`。
- Label 表仅 `default` + **`gameplay`**(Gameplay 组各 folder 均已打;子资产继承)。
- 现有预热两级:`WarmEssentialAsync`(硬编码 path 小集,启动时)与 `WarmRegistryAsync`(注册表 AssetReference 全表,进地牢门控时)。后者只覆盖"注册表能枚举的资产",Gameplay 组中**表外资产**(敌人生成器、门、瓦片、交互物、地牢结构、特效等)未被预热 —— WebGL 下是潜在同步访问隐患。

### 12.2 初版策略(资源量小的当下)

**决策**:初期内容与关卡少,**不做 Band/Label 收敛,直接按整个 Gameplay 组预载**,换取加载逻辑最简单、且一次堵住全部同步访问隐患。两槽:

| 槽 | 内容 | 条目来源 | 触发/门控 | 释放 |
|---|---|---|---|---|
| **Essential** | 全局 Config + 默认图标 | `path` 小集(≈ 现有 WarmEssential) | 启动(Logo 前) | Persistent |
| **Gameplay** | 整个玩法组(含注册表资产与表外资源) | **label `gameplay` 整组** | 进入地牢前(Loading 门控,替代现有 WarmRegistry) | Manual/随离开地牢释放 |

Gameplay 槽按 label 整组,覆盖并**取代** `WarmRegistryAsync` 的注册表全表语义,同时补上表外资源的预热,消除 WebGL 表外同步抛的隐患。

### 12.3 演进触发与路径(不提前实现)

当内容/关卡增多、整组预载的加载时长或 WebGL 内存成为问题时再演进:

1. 给 Gameplay 组内的内容打 **Band label**(按出现楼层段粗分,自动打标动作并入 JASA `刷新数据表` 编辑器流程);
2. Gameplay 槽退化为"当前 Band + 下一 Band"的 label 集合(或按需逐条);
3. 需要 bundle 级隔离时,再按 Band 拆 Group。

**演进不破坏框架**:槽内容从"一个 label"变"多个 label / 逐条",`PreloadService` 接口与 Profile 三条目形态不变,只改打标粒度。
